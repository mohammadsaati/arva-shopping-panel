# Project rules

## Application architecture

- Keep runtime application database reads and writes in Eloquent model methods. Services call those model methods, but must not use Eloquent query builders, `save` or `delete` directly, the `DB` facade, or raw SQL. Controllers only call services. Migrations, factories, and seeders are exempt.
- In every Eloquent model, document each persisted column with a PHPDoc `@property` entry. Keep the PHP types, nullability, enum casts, and timestamp types in sync with the migration and model casts.
- Declare `#[Guarded('id')]` on every Eloquent model so model and factory persistence can mass assign validated fields while keeping the primary key protected. Import `Illuminate\Database\Eloquent\Attributes\Guarded`; do not replace this rule with a `$fillable` or `$guarded` property.
- Order model methods consistently: relationship methods first, Eloquent local scope methods (`scope...`) next, then casts and all other query, create, update, and helper methods.
- Put business decisions and workflows in classes under `app/Services`. Every service must implement an interface under `app/Services/Contracts`, and its interface must be bound to its implementation in `AppServiceProvider`.
- Controllers must depend on service interfaces. Keep controllers focused on HTTP input and output; put request validation in Form Request classes and pass validated data to services through DTOs.
- In create/store actions, construct DTOs inline with named arguments from typed Form Request accessors (`string('field')->value()` for strings and `enum('field', Enum::class)` for enums). Keep snake_case request-to-camelCase DTO mapping at the controller boundary and do not pass an intermediate `$request->validated()` array into the DTO.
- Wrap forms with the shared `<x-card.form>` component and use its shared field components instead of raw form controls.
- Design admin create and edit forms as task-focused cards. Use `<x-card.form class="admin-editor-form">`, a short `<x-admin.form-intro>` at the top, and separate `<x-admin.form-section>` cards for related fields such as identity, placement, media, publishing/status, pricing, and advanced settings. Put the primary fields in `.admin-form-main` and secondary settings in `.admin-form-sidebar` within `.admin-form-layout` when a form has enough fields; use `.admin-form-layout--single` for short forms. Give each section a clear title and concise help text, and keep the layout usable on mobile. Existing blog forms already have their own equivalent card layouts and should retain those patterns.
- When reorganizing admin forms, preserve every field name, value or `old()` binding, validation message, conditional field, file input, Livewire picker, and submit behavior. Keep status defaults tied to the appropriate enum case's `->value` rather than hardcoded strings. Place the save and cancel actions in the shared form action area.
- Update DTOs must check for null or omitted values and expose only fields intended for the update, so omitted fields do not overwrite stored values.
- Declare every admin route in `routes/admin.php`; do not place admin endpoints in `routes/web.php`. Group each admin resource by controller with `Route::controller(Controller::class)->prefix('users')->name('users.')`, then define routes by HTTP verb and relative path with a short leaf name such as `index`, `create`, `store`, or `show`. Put static paths before dynamic placeholders and constrain numeric IDs with `whereNumber()`. `bootstrap/app.php` supplies the `/admin` URI prefix and `admin.` route-name prefix, so do not repeat them in `routes/admin.php`. Admin pages must use the shared `<x-panel-layout>` Blade component and its shared layout partials for the sidebar, header, and footer.
- Keep public blog endpoints in `routes/blog.php` and register that file through `bootstrap/app.php`; do not put blog routes in `routes/web.php`. Declare blog admin endpoints in `routes/admin.php` under the `admin-blog` URI and route-name prefixes, which combine with the bootstrap `/admin` and `admin.` prefixes. Keep the blog navigation as its own top-level group in `AdminMenu`, separate from storefront content navigation.
- Load admin navigation from `MenuRegistry::visible('admin')` and define its entries in `App\Commons\Menu\Menus\AdminMenu`; do not hardcode admin menu entries in Blade views.
- Enums use `LabelTrait` and `ValuesTrait`: `trans()` resolves `enums.<backing-value>`, or `enums.<labelKey>.<backing-value>` when `labelKey()` is overridden. Add a translation for every enum case in each supported locale's `lang/{locale}/enums.php`, importing the enum and using `EnumName::CASE->value` as the key. Use `EnumName::toKeyValueType()` for translated option labels instead of hardcoding enum labels. When displaying a model's enum value in a detail view, use the enum instance's `->trans()` method directly; do not prepare label maps in the controller or hardcode translated labels in Blade. For enum-driven badge colors, define a `color()` method on the related enum and use it from the view instead of branching on enum cases there. Keep `toKeyValueType()` for translated option lists and filter labels. Every persisted status or approval-state column must use a backed enum; reuse an existing enum only when its states have the same meaning, otherwise create a dedicated enum. Cast status columns to their enum in the model. Store these columns as strings and set migration defaults with the matching enum case's `->value`, never a hardcoded status string.
- Format dates shown in Blade with the global `jalali_date($date, $format = 'Y/m/d')` helper, which uses the installed Verta package. Pass an optional Verta format when needed and keep a fallback for nullable dates. Do not format displayed dates directly with Carbon or `DateTime::format()`.
- Render record collections as table rows, not as separate cards for each record. Use the shared `<x-datatable>` component for tables, with the table container it provides.
- When a table row has multiple actions, use the shared `<x-table.actions>` component to group them in one compact, accessible dropdown instead of showing several buttons inline. Put each action in the component slot as a menu link with an icon and clear label.
- Use `simplePaginate()` for list queries instead of `paginate()`.
- Define a shared `BaseFilterData` DTO with `perPage`, `page`, and `sorts`. Each list-specific filter DTO must extend it and declare its criteria as typed readonly properties; do not put list criteria in a generic `filters` array. Livewire list components must map their state into one DTO and call the service interface, converting scalar values to enum cases when the DTO expects enums. Keep database queries in model methods according to the application architecture rules.
- In list model methods, apply optional DTO criteria with Eloquent `when()` clauses, allowlist sort columns before applying the DTO's sort directions, and return `simplePaginate(perPage: $filters->perPage, page: $filters->page)->withQueryString()`.
- List-page controllers must return the Blade page without loading or passing list data. Mount a Livewire component inside that page; the Livewire component loads and renders the filtered, simply-paginated table.
- Provide filter controls for list tables and use the shared `<x-datatable>`, `<x-datatable-heading>`, and `<x-pagination-bar>` components where applicable. Follow `/Users/mmd/Projects/buty-panel/laravel-panel/resources/views/livewire/banners/banner-table.blade.php` for the filter, sorting, table, and pagination pattern.
- Keep one table creation per migration file. Store status columns as strings with a default taken from the appropriate enum case's `->value`.

## Public storefront

- Build customer-facing pages on `<x-user-layout>`. Keep the shared storefront header and footer in the Blade components `<x-user.header>` and `<x-user.footer>`; the layout renders them. Do not duplicate their markup or include them as partials in individual pages.
- Use `<x-user-panel>` for customer pages that need a page title, subtitle, or action area. Keep the storefront home page at the named `home` route, handled by `HomeController@index` returning `home.index`; render its featured catalog through `<livewire:storefront.home-catalog />`, so the controller and route view stay free of list data.
- Build the storefront category mega menu from active parent categories and their active children; show parents in a menu list and reveal each parent's children on hover, focus, or tap. Category menu links must not filter the home page catalog by category.
- Keep the desktop storefront header and the separate `<x-user.mobile-header>` view for screens below 1024px. Follow the Karin mobile structure: top bar, slide-out menu, category and child-category views, full-screen search, and a fixed quick-access bottom bar. Show each category's image when present and its saved icon, provide keyboard back/close controls, and keep category links from filtering the home page catalog.
- Load featured categories and products through a Livewire component and a service contract bound in `AppServiceProvider`. Keep their queries in model methods, show only active categories/items/products and in-stock products, and cap these homepage sections rather than paginating them. Use product and category cards on the storefront; the table rule applies to admin management lists.
- Render public asset and storage image paths with the shared `public_image_url($path)` helper instead of repeating path checks in Blade.
- Keep the user-facing theme RTL and use the Karin stylesheet and fonts copied under `public/assets/karin`; treat the sibling `karin` folder as a read-only design reference.
